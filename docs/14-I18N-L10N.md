# 14 — Internationalization & Localization

> **Status:** Draft · **Version:** 1.0 · **Owner:** Frontend + Product · **Last updated:** 2026-08-18
> **Authoritative for:** locale negotiation, translation workflow, formatting, RTL, multilingual content handling.

## 1. Scope

Internationalization (i18n) is the engineering work that makes localization possible: no hardcoded
strings, no baked-in formats, no layout that assumes English. Localization (l10n) is the content
work: translations, regional formats, locale-specific policy text.

This applies to the web application, email templates, notifications, exported documents, API error
messages, and the sync/desktop clients. It does not apply to log output or audit records, which stay
in English with stable machine codes so support and forensics are consistent worldwide.

## 2. Launch locales

| Tier | Locales | Commitment |
|---|---|---|
| Tier 1 | `en-US`, `en-GB`, `en-IN` | Full UI, email, docs, support |
| Tier 2 | `de-DE`, `fr-FR`, `es-ES`, `ja-JP`, `pt-BR` | Full UI and email |
| Tier 3 | `hi-IN`, `ar-AE`, `zh-Hans`, `ko-KR`, `it-IT`, `nl-NL` | UI; RTL validated via `ar-AE` |

`ar-AE` is in the launch set specifically to keep RTL honest. An RTL locale added later always
uncovers layout assumptions that were cheap to avoid and expensive to retrofit.

## 3. Locale resolution

Precedence, first match wins:

```text
1. Explicit user preference        (users.locale)
2. Tenant default                  (tenants.settings.default_locale)
3. Accept-Language negotiation     (best match against supported locales)
4. Platform fallback               (en-US)
```

Resolution uses BCP 47 with proper fallback chaining: `fr-CA` → `fr` → `en-US`. The resolved locale
is returned by `/api/v1/bootstrap` and echoed in `Content-Language`.

Time zone is resolved separately from language — an engineer in Bengaluru may want an English
interface and IST timestamps. `users.timezone` defaults to the browser's IANA zone, and every
timestamp is rendered in it, never in UTC or server-local time.

## 4. Application implementation

- **Library:** `react-intl` (ICU MessageFormat) or `i18next` with the ICU plugin. ICU is required,
  not optional — plural and gender rules in Slavic, Arabic and South Asian languages cannot be
  expressed by simple key/value substitution.
- **No concatenation.** `"Deleted " + n + " files"` is a defect. The message is a single ICU string
  with placeholders and plural categories:

```json
{
  "files.deleted": "{count, plural, one {Deleted # file} other {Deleted # files}}",
  "share.expires": "Access expires {date, date, medium} at {date, time, short}",
  "quota.usage": "{used} of {total} used ({pct, number, percent})"
}
```

- **Keys are namespaced and stable**: `files.actions.download`, `admin.dlp.policy.simulate`. Keys are
  never derived from English text, so wording changes do not orphan translations.
- **Context for translators.** Every key carries a `description` explaining where it appears and what
  the placeholders mean. "Share" as a verb and "Share" as a noun are different keys with different
  descriptions, because they are different words in most languages.
- **Lazy loading.** Locale bundles are code-split and fetched on demand; only the active locale is in
  the main bundle.

## 5. Server-side localization

Some text originates on the server and must be localized there:

| Surface | Approach |
|---|---|
| API error messages | The API returns a stable `code` plus an English default; the client renders its own localized string keyed by `code`. This keeps the API locale-independent and the client authoritative for wording. |
| Email and notifications | Rendered server-side in the **recipient's** locale — not the actor's. A German user receives a German "shared a file with you" even when the sharer's interface is English. |
| Exported documents and reports | Rendered in the requester's locale, with the locale recorded in the export metadata. |
| Watermarks | Rendered in the viewer's locale, with the timestamp in the viewer's time zone. |

Server-side message catalogs live alongside the client catalogs and share the same keys where the
text is the same, so a wording change lands once.

## 6. Formatting

All formatting goes through `Intl` (client) and ICU (server). Nothing is hand-rolled.

| Type | Rule |
|---|---|
| Dates | `Intl.DateTimeFormat` in the user's time zone; relative dates ("2 hours ago") via `Intl.RelativeTimeFormat` with an absolute value in the tooltip |
| Numbers | `Intl.NumberFormat`, including the Indian digit grouping (`12,34,567`) which naive formatters get wrong |
| File sizes | Locale-aware units, binary or decimal per tenant preference |
| Currency | `Intl.NumberFormat` with explicit currency; never assume USD |
| Names | Display the full name as provided; never assume given-name-first ordering or split on whitespace |
| Sorting | `Intl.Collator` with the active locale — German ä, Swedish å and Chinese pinyin all sort differently from a byte comparison |
| Addresses/phones | Free-form with locale hints; no fixed-format validation |

Server-side sorting for paginated lists uses a PostgreSQL collation matching the requested locale
(`ORDER BY name COLLATE "de-DE-x-icu"`), so page 2 continues where page 1 ended. Mixing a client
collator with server pagination silently reorders across page boundaries — a subtle bug worth
avoiding by construction.

## 7. Layout, RTL and text expansion

- **Logical CSS properties everywhere**: `margin-inline-start`, `padding-inline-end`,
  `border-start-start-radius`. No `left`/`right` in layout CSS.
- `dir="rtl"` on `<html>` for RTL locales; the entire layout mirrors, including navigation, table
  column order, progress direction and chevrons.
- **Icons that encode direction** (back, forward, indent, next page) mirror. Icons that do not
  (clock, checkmark, logo) never mirror.
- **Text expansion budget: 40%.** German and Finnish routinely run 30–40% longer than English.
  Buttons, table headers and navigation must not clip or wrap awkwardly at +40%; the pseudo-locale in
  `§9` enforces this in CI.
- **No text in images.** Any label inside an illustration is an SVG `<text>` element or overlaid DOM.
- **Bidirectional content.** File names mixing Arabic and Latin script are wrapped with Unicode
  isolates (`<bdi>`) so a right-to-left name cannot rearrange the surrounding UI.

## 8. Engineering rules

Enforced in CI (`12-TESTING.md §5`):

1. No user-facing string literal in `web/src` outside a catalog — a lint rule with a narrow
   allowlist for developer-only debug text.
2. Every catalog key referenced in code exists in `en-US`; every key in a translation exists in
   `en-US`. Orphans and missing keys both fail the build.
3. No date, number or currency formatting outside the `Intl` wrappers.
4. No `left`/`right` physical properties in component CSS.
5. Every new key ships with a translator description.
6. Missing translations fall back to `en-US` and render normally — a missing string never renders a
   raw key or an empty element in production.

## 9. Pseudo-locale testing

A generated `en-XA` pseudo-locale runs in CI and is available in staging:

```text
"Download"  ->  "[Ḋøŵñļøàđ ‹››››››››››]"
```

It simultaneously catches three things: unlocalized strings (they appear in plain ASCII), text
expansion overflow (the padding forces +40%), and character-encoding problems. A matching `en-XB`
pseudo-locale flips text direction to catch RTL layout defects without needing an Arabic speaker.

## 10. Translation workflow

```text
Developer adds key + en-US text + description
  -> CI extracts the catalog and opens a translation task
  -> Translation platform (Crowdin / Lokalise / in-house) receives it with screenshots
  -> Translators work with visual context, not a spreadsheet
  -> Reviewed translations merge back as a normal PR
  -> Release ships complete locales; incomplete locales fall back per key
```

Machine translation may seed a locale but never ships to Tier 1 or Tier 2 without human review.
Security-critical text — policy denials, consent screens, deletion confirmations, legal-hold notices
— is always human-reviewed, because a mistranslated "this cannot be undone" is a data-loss incident.

## 11. Multilingual content and search

The interface language and the content language are independent. A tenant may run an English
interface over documents in Japanese, German and Hindi.

- Document language is detected during extraction and stored per chunk (`language` field,
  `07-SEARCH-INDEXING.md §4`).
- Lexical retrieval uses a language-appropriate analyzer: CJK segmentation for Chinese, Japanese and
  Korean; stemming for European languages; no naive whitespace tokenization, which fails outright on
  CJK.
- Dense retrieval uses a multilingual embedding model where the tenant has mixed-language content, so
  a query in English can retrieve a Japanese document about the same subject. The model choice is a
  tenant configuration, because a monolingual model is better for a monolingual corpus.
- Search filters may restrict by content language; results display the detected language when it
  differs from the interface language.
- Optional query translation is off by default and, when enabled, routes through the same
  classification-aware `LlmProvider` rules as any other generative feature
  (`08-BYO-INFRA.md §12.2`).

## 12. Locale-sensitive policy and compliance

Some governance text is jurisdictional, not merely translated:

- privacy, terms and support links are per-tenant **and** per-locale (`09-UX-WHITE-LABELING.md §18`);
- consent and disclosure text (recording, watermarking, monitoring notices) is localized and
  version-tracked, since the notice a user actually saw may matter later;
- classification label names are tenant-defined and separately localizable — a tenant may want
  "Vertraulich" displayed for `CONFIDENTIAL` while the key stays stable in policy and audit.

Audit records always store the stable key, never the localized label. A German admin's action and an
English admin's action must be the same event in the log.

## 13. Client localization

Desktop and mobile sync clients localize their own UI from the same catalogs, and follow the OS
locale by default with an in-app override. Notifications from the client are localized to the client
locale; notifications from the server are localized to the user's stored locale — these can differ,
and the stored preference wins for anything the server generates.

Path and file names are handled as opaque Unicode: NFC-normalized for comparison, preserved as
supplied for display, with per-platform handling of case-insensitive and NFD-normalizing file
systems (`10-SYNC-AND-EDITING.md §6`).
